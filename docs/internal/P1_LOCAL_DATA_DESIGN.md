## 2. 必须保持的业务不变量

1. 先保存本机事实，再反馈“已保存在本机”；离线和电脑关闭不影响本地事务。未获对端持久确认不能显示“已同步”。本地提交不等待模型、地图、DNS或连接层。
2. 同一已提交操作只生效一次；同ID不同语义明确拒绝。失败不能只落账目却缺历史／操作回执，也不能只存待同步项却没业务变更。进程在提交后、桥接返回前退出，重试仍返回原结果。
3. 当前分支指向新的不可变业务修订；旧修订与其附件引用不改。用户可以明确更正／删除当前账目并留下历史，保护不等于永久禁止纠错；模型／规划结果不得替用户改实付、付款事实、回款或预约。
4. 行程日、付款日、预约当地时刻、记录创建时间分别表示不同事实。设备切时区、改行程顺序或重新生成路线，不自动改写付款日、稳定活动ID或预约时刻。
5. 预算／预测／未知费用与实付分开；未知不是0。退款与报销有独立记录、状态及原消费引用；不得通过改原消费金额表达退款或将报销重复冲减消费。
6. 删除、撤销、合并均是显式业务操作；历史及待同步删除记录保留。不能以清库、按更新时间覆盖整份旅行、复制活跃SQLite或重新生成所有ID解决冲突。
7. 凭据、设备私钥、配置秘密与本地文件绝对路径不进入业务快照／变更包／附件元数据。设备ID只识别来源，不代替配对认证；脱敏诊断也不输出整份旅行。

## 3. 金额、日期和身份的草案表示

### 金额

推荐新写入边界直接收经过十进制校验的整分，避免JS先以浮点乘100。是否使用JSON整数由两端评审：沿用现有安全整数范围更便于复用投影，但必须在桥接和原生落库前重复校验，不能依靠SQLite整数容量替代跨语言上界。输入框从十进制文本精确转换，拒绝指数、NaN、Infinity、非正实付／回款、超两位小数与溢出，不静默四舍五入或截断。

单笔录入上界与汇总上界分开：电脑当前Decimal录入约束对应最多`99,999,999.99`元，即`9,999,999,999`分；它小于只读投影允许的正安全整数上界。建议写入先对齐现有录入范围，不以P0大数样例扩大正式录入能力；最终上下界及空白／前导零／小数点语法需固定跨语言样例。每笔、每种汇总、中间累加与净额都检查安全整数范围，溢出拒绝整笔事务。金额编码、币种是否显式携带及旧超界数据处理仍是差异项，不新增多币种换算或把旧数值裁剪成上限。

### 日期与时区

| 语义 | 建议表示与处理 | 旧数据／未决项 |
| --- | --- | --- |
| 行程日 | 保留day序号及稳定活动关联；若增加日期，显式记录旅行日历映射 | 不能把day=2直接换成付款日期；修改出发日的联动规则待评审 |
| 付款日 | 用户2026-11-14已确认与行程日分开；新建消费默认填手机当前日期，可修改，保存后不随时区／行程调整自动改变。确有付款时刻时另存带偏移的时刻及适用时区，具体编码待评审 | 旧模型无此字段，缺失保持未知；编辑旧记录不默认补今天，不拿created_at／行程日补造事实 |
| 预约 | 保留当地时钟、start_day_offset与duration_minutes；建议补明预约所在地时区和关联旅行日历版本 | 旧Booking未编码时区；不能以手机当前时区默补。夏令时不存在／重复的时刻应提示并选择，不能偷偷挪动 |
| 创建／修改时间 | 新记录建议存明确定义的时间戳，仅作审计与展示 | 旧datetime来源可能无偏移，转换须保留未知来源；不作冲突排序或付款日权威 |

预填仅用于新建消费表单：保存用户提交的表单值，不在提交瞬间以当前日期覆盖；手机日期只是可修改的输入建议，不是付款事实的外部证明。旧记录编辑保持未知状态，除非用户明确补录。本轮只确认该使用规则，未注册字段、实现表单或写入数据库。

例如，用户确认付款日为`2026-11-14`，同时记录的时刻为`2026-11-14T00:30:00+09:00`；手机切到America/Los_Angeles后，这个时刻的当地展示为`2026-11-13 07:30`，付款日仍是`2026-11-14`。预约`23:40`／offset=0／120分钟，结束为次日`01:40`；不能将offset丢弃或把预约转换成手机所在时区的同名时钟。日历、时区库／数据版本与旧记录映射另给共同样例，本稿未新增日期算法。

| 身份／版本 | 建议职责 |
| --- | --- |
| 旅行／分支／业务实体ID | 稳定且不由显示名称、数组位置或当天顺序生成；导入保留原ID，不强制把旧ID改成UUID。新ID格式／冲突域待共同固定 |
| 设备／安装身份 | 用于来源和去重；正常重开／升级不换身份。恢复备份、重新安装和多模式共存需另定防碰撞／重新配对流程，不能克隆身份冒充原设备 |
| 操作ID | 创建、编辑、删除、撤销都各有操作ID；重试复用原ID与原语义。与实体ID区分；电脑现有创建request_id同时充当记录ID，适配需明确映射 |

## 4. 本地命令与事务边界

建议应用用例通过窄命令提交语义数据，至少包含契约标识／版本、操作ID、来源身份、目标旅行／分支、期望基线、命令类型和参数。以下是语义族，**不是现有或已经确定的API名**：

| 命令族 | 应保护的状态与边界 |
| --- | --- |
| 消费／回款创建、更正、删除 | 金额、付款事实、预算／活动／票据关联与回款上限；同ID重放与关联删除规则 |
| 进度／预约更新 | 实际停留点、执行状态、当地时间与跨日偏移；已有执行记录时不能绕过规则直接更改预约 |
| 旅行／分支／版本／主方案操作 | 历史只读、主方案及父修订可追溯；只读历史编辑应成为显式新分支／修订，不原地改快照 |
| 计划／AI／高级工程结果采用或撤销 | 在线结果先存候选，应用时核对基线并重新执行保护规则；不能直接整包覆盖已记录事实 |
| 文件引用、回顾、偏好与工程本地管理 | 保护引用、权限和离线可读；设备配置与旅行数据分开。完整字段与规则按能力矩阵逐项补齐，不将本稿当仅支持记账的范围缩减 |

原生层负责最终边界校验及事务提交，不能因为TS已经校验就信任页面提交的总额、权限、SQL或文件路径。TS可复用领域计算与交互预检；规则所有权和两端参考样例需明确，避免两套校验悄悄分叉。建议第一版按分支串行提交并核对基线，在跨仓确认前不采用字段级自动合并或通用CRDT。

建议单次提交顺序如下：

1. 检查命令格式、来源／调用权限及支持版本，在固定编码规则下形成可比较语义。格式规范必须涵盖null／缺省、数组顺序、字符串和数字；不能随意用JSON.stringify结果充当跨语言指纹。摘要算法及测试向量待定，保留必要语义以诊断同ID不同内容。
2. 在同一受控写事务中先查操作回执：同ID同语义且已提交，返回原修订／结果；同ID不同语义，拒绝且原库不变。**已提交重放先于期望基线检查**，否则成功后回执丢失的重试会被错误判为过期。
3. 对新操作核对目标当前修订及删除状态，重新检查金额、日期／预约、预算／附件和全部关联约束。基线过期时返回可重新读取的冲突，不偷偷重定位到最新修订重放。
4. 原子写入业务新状态／不可变修订、分支头、操作回执、删除记录和待同步变更记录；派生账目从当前有效记录计算，不能把每个历史修订都重复计入。字段布局、快照或增量实现、索引及SQLite参数需后续评审，当前不建表。
5. 提交成功才回执本机保存；界面更新为“本机已保存／等待连接”。连接任务在事务外运行。这里的待同步记录是预留持久事实，不是已经可发出的协议包；协议／配对未就绪时不得发送或显示对端已确认。

中止前未提交：整笔无效，不能增加实付、修订或待同步项。提交后桥接断开：结果可能已成功，客户端保留原操作ID，查询原回执／同内容重试；不生成新ID补记。提交返回错误但结果不明时进入“结果待核实”，重新打开读取回执后判定，不能一律显示“未保存”诱发重复录入。读取失败／库损坏与空库分开，不创建空库覆盖原文件。

操作回执、删除记录和历史何时可清理需包含所有配对设备的持久确认／撤销策略；未定义前不按时间自动清除。界面撤销也生成新操作及修订，不能删掉已经确认的原操作来伪装从未发生。

### 附件与迁移

SQLite和文件系统不在一个事务。建议先把内容导入本应用拥有的暂存区，验证大小／类型／摘要并完成持久化，再让业务事务引用已就绪内容；业务提交后才清理暂存／旧引用。提交前退出留下的未引用内容可按明确归属清理，提交后退出的内容必须仍可读取；所有历史／待同步／备份引用都释放后才能物理回收。不得接受页面传入任意路径，不扫删其他应用文件，也不将content URI字符串当已永久复制成功。

磁盘满、权限失效、照片导入中断和附件缺失须有可恢复状态，不报告整笔完成；外部分享／系统选择器授权和跨卷移动需平台适配另验。文件就绪与数据库引用之间的崩溃点、备份一致性、恢复校验及清理时机均是实现前待细化项，不承诺简单rename能覆盖所有存储条件。

表结构升级须有旧版拒绝不兼容写入、隔离副本演练、恢复点及新增数据保全方案；回退不能直接用旧备份覆盖升级后新账目。P0的org.travelflow.p0虚构库不自动迁入正式产品。备份不含凭据，且不能用复制运行中的数据库文件充当业务同步。当前不迁移、清除或导出任何真实数据。

| B1 | 已预约、未开始的站点被AI省略或改时；改变其前一站 | 预约地点／时刻／停留和稳定ID保留；改变起点后交通估算失效需独立重算，不能保留旧交通冒充有效 |
| B2 | completed站点尝试改预约；规划起点尝试记实付／实际到访 | 遵守现有执行保护及实际停留点规则；明确人工恢复状态的流程需单独命令，不因AI应用而绕过 |
| H1 | 分支v1有实付10000；v2重规划并改预算；查看v1 | v1逐字段与附件引用不变；v2实付仍10000且不计成20000，预算未知仍未知，不从预算推造实付 |
| H2 | AI任务基于v1运行；期间用户在v2记账，AI结果返回 | 保存为候选并检查基线，不整包覆盖v2；如何重算／重新预览／保留分支留显式决策，不能静默丢账 |
| X1 | 有回款的消费被删除；同时另设备离线编辑该消费 | 本地直接删消费先拒绝；未来收到删除／编辑并发形成可恢复冲突，不级联删回款、不按时间胜负 |
| X2 | 活动被移除但已有实付；旧设备仍带原关联 | 保留消费原金额及付款事实；解除／保留关联、预算结算与历史引用按共同规则记录，不能按标题挂到另一站。电脑当前可能解除activity／预算链接，跨端含义待评审 |
| T1 | 在写业务、历史、回执、待同步项各步骤故障／磁盘满；提交后返回前杀进程 | 要么整体未提交，要么完整已提交且同ID可查回；不出现半笔账或两个有效提交。具体故障点由正式存储原型验证 |
| F1 | 导入票据后提交前退出／提交后退出；旧版本仍引用被当前版本移除的票据 | 分别可回收明确归属的未引用内容／可恢复已提交引用；历史引用存在时不得物理删文件 |
| V1 | 不支持的命令／存储版本、损坏记录或未知字段进入写路径 | 在写入前拒绝／隔离并可诊断，旧账与原文件保留；不能默默丢字段、清空重建或假装迁移成功 |

其中M3／M4及M6的只读汇总可用当前ledger0.1.0核算；M5为录入保护，不能拿允许超额旧数据的投影反证。每个写入样例后续需同时给Python权威结果、TS领域校验和Android真实落盘／故障结果，分别标版本，不仅比较页面数字。

## 6. 跨仓差异与实现前待定项

这些是需电脑侧共同评审的差异，不是要求用户猜内部API，也不自动授权向他人发消息。本仓库先形成可评审草案，由用户协调电脑仓库工作；任何快照升级都需双方固定提交与样例。

| 差异 | 当前依据／风险 | 收口需要的结果 |
| --- | --- | --- |
| 金额编码、上界与币种 | Decimal录入、整数持久化、只读安全整数是三个范围；账目未有币种字段 | 明确新命令整分／文本编码、上下界、累计、旧超界处理和币种语义，共同向量；不盲目放宽或截断 |
| 付款日与预约时区 | 当前Expense仅day＋创建／修改时间，Booking无时区 | 新旧字段映射、缺失状态、旅行日期变更与时区／夏令时样例；不得伪造旧付款日 |
| 操作ID与删除重放 | 电脑创建request_id兼作实体ID，编辑／删除未在只读契约中定义幂等 | 所有命令的去重域、同ID不同内容、回执编码与保留；已删除实体不因旧操作重放复活 |
| 历史／分支／修订映射 | 电脑现有版本不是已经定义的同步修订；本地seq不可跨设备比较 | 稳定身份、父修订、主方案、显式撤销、删除／归档和历史读规则；不以整份覆盖合并 |
| 关联与旧数据 | 新回款拒绝孤立，读投影兼容旧孤立；移除活动可能解除链接／结算标志 | 新写入约束与旧导入兼容分开；活动／预算／票据引用保留、解除或冲突的明确结果 |
| 本地事务与文件持久化 | 探针仅固定记录，没有完整历史／回执／待同步／附件原子语义 | 正式存储技术／配置、恢复状态机、磁盘满／崩溃点与一致性备份设计，先在虚构库验证 |
| 规则所有权及全能力覆盖 | TS可移植领域与原生最终校验、Python权威规则需一致；本稿不覆盖全部字段 | 按能力矩阵把LOCAL／MIXED的本地部分逐项映射命令、领域规则及保护样例；补规划／回顾／模板与工程规则，不能只交付记账 |
| 交换与配对 | 完整同步协议、附件清单／确认与连接工具未定 | 单所有者设备身份／认证、兼容协商、共同基线、并发／删除冲突、确认／保留规则；不先启用传输或接入第三方账号 |

本稿已形成第一轮设计和第7节具体评审样例。下一步由两端共同核对金额／日期／身份与版本样例及差异，再形成带版本的写入契约候选与原生事务接口／恢复设计；规则充分明确后才安排虚构数据的正式存储最小闭环。P0正式传输、系统兼容与真实供应商门槛另行推进，不因本地设计启动而消失；全仓跨端P0不据此宣布结束。

## 7. 固定源码复核与具体评审样例

2026-11-14通过GitHub只读核对电脑main为`23236a6c46bf5f3c7ca8966250413aa2f4722dfb`。与首稿基线`7e2bb600e030385398cbf1e2dc9c59d4d6d7a850`[比较](https://github.com/wuqiuwangtian/TravelFlow-AI/compare/7e2bb600e030385398cbf1e2dc9c59d4d6d7a850...23236a6c46bf5f3c7ca8966250413aa2f4722dfb)为ahead21、27个变更路径，集中在桌面启动／界面／检查与文档，未改变本稿核对的backend领域、旅中／回款服务、行程路由、版本模型／存储或只读共享契约。本轮仅固定该提交作复核依据，没有拉取电脑main、改动电脑仓库或导入新vendor快照。

新增[机器可读评审资料](fixtures/p1-review-cases.json)。review_format_version=1只标识此资料的组织格式，shared_contract_version仍为null，desktop_joint_review仍pending。它不是共享写入契约，也不是电脑侧已经认可的参考输出。资料记录固定提交、源文件Git blob SHA及符号；本地检查器仅检查这些引用的结构／关联，不联网核验来源或提供签名背书。

| 部分 | 当前能执行或确认什么 | 当前不能证明什么 |
| --- | --- | --- |
| L01–L06 | 用现有TS只读投影核算6组虚构金额，包含pending／received、负净额、旧孤立回款和大数边界；不修改输入 | 单笔写入校验、退款状态转换或Python参考结果已经共同确认 |
| C01–C02、K01–K02 | Node Intl核算带明确偏移时刻在两个时区的日历日，整数算术核算两组跨日时钟 | 付款日持久保护、预约时区／夏令时策略、Android日期适配或迁移 |

只读入口为仓库根目录`pnpm check:p1-review`，需要Node22+和既有pnpm依赖，不需要Python依赖、SDK、ADB、设备、数据库、密钥或测试服务。输出应为6组只读投影、2组时区换算、2组时钟计算、12项差异编目，且python_backend_executed=false、mobile_write_scenarios_executed=0及联合评审pending。可向`node scripts/check-p1-review.mjs PATH`提供评审JSON副本核对；它不执行其中的业务步骤。CI加入相同入口，不把工具检查成功等同正式契约通过。

### 需要电脑侧核对的具体行为

- **S04／S05：原操作结果与当前状态分开。** 固定[创建路由](https://github.com/wuqiuwangtian/TravelFlow-AI/blob/23236a6c46bf5f3c7ca8966250413aa2f4722dfb/backend/app/api/routes_itinerary.py#L812)读取latest后去重，同内容重试返回当前latest；创建后再更正金额，原创建内容则与当前实体不同而冲突。P1建议返回原操作回执，同时不把旧内容重新应用；界面若需最新状态另读，不能用旧回执覆盖新账目。
- **S06／S07：删除重放与过期基线是两条路径。** [当前服务](https://github.com/wuqiuwangtian/TravelFlow-AI/blob/23236a6c46bf5f3c7ca8966250413aa2f4722dfb/backend/app/services/travel_service.py#L61)只在当前列表中查创建ID。无回款消费被删除后，使用当前最新版本再次提交旧创建ID可走新建路径；使用过期版本且无匹配记录则在路由中冲突、不进入保存。这是有条件的源码推导，未运行故障复现，不能泛化为所有旧请求都会复活。
- **S08：原保存事实与票据当前可读分开。** `_validate_receipts`在创建去重前执行，票据不可用时可能先拒绝。持久回执应能确认原保存事实，权限／票据当前状态另作处理，不能把已经保存误报成从未提交。
- **S09／S10：现有版本不是现成的操作协议。** [版本模型](https://github.com/wuqiuwangtian/TravelFlow-AI/blob/23236a6c46bf5f3c7ca8966250413aa2f4722dfb/backend/app/domain/models.py#L149)的seq与checkpoint_id不提供共同因果关系；`_save_revision`跨图状态更新和[多个存储提交](https://github.com/wuqiuwangtian/TravelFlow-AI/blob/23236a6c46bf5f3c7ca8966250413aa2f4722dfb/backend/app/storage/session_store.py#L333)。未证明其与回执／待同步记录原子提交；不据源码推导断言现有库实际丢失数据，也不把一次桥调用当一个存储事务。
- **S12：不能盲目向旧接口增加付款日等字段。** 固定ExpenseInput直接继承BaseModel且没有extra配置；[Pydantic官方说明](https://docs.pydantic.dev/latest/api/config/#pydantic.config.ConfigDict.extra)的默认行为是忽略未声明字段。因此推断旧输入可能接受请求却不保留新增语义。当前未执行电脑所固定的Python模型／HTTP验证；共同协议必须明确能力协商与未知字段拒绝，不能仅凭旧接口返回成功就宣称付款日受保护。

### 跨仓评审应返回的结果

1. 对S01／S11给出电脑侧固定版本的录入与只读样例结果，明确整分编码、单笔／累计上界、回款按种类含pending的限制及旧数据处理；不能只再生成一份14项只读快照。
2. 对S02／S12明确独立付款日、预约时区与旧记录未知状态的字段映射、兼容能力和未知字段处理。付款日默认规则已由用户确认，见第3节及S02；字段／未知状态与旧端兼容仍待共同确认，不能把产品选择当作共享契约已经接受。
3. 对S03–S09明确实体／操作／业务修订／本地seq映射，以及重试、更正、删除、恢复、分叉／主方案的响应和冲突含义；为“提交后回执丢失”“更正后重放”“删除后重放”分别给共同预期。
4. 对S10及T1／F1提出电脑与Android各自的提交、恢复及文件一致性设计／待验故障点，记录双方固定提交及接受／修改／待定项。当前资料中的pending不由任何一端单方面改为联合通过。

上述结果齐备后再固化带版本的写入契约候选、事务接口及恢复状态机。可以先完善不受待定项影响的设计，不能默认电脑会立即升级、自动对外发消息或实施真实数据迁移。
