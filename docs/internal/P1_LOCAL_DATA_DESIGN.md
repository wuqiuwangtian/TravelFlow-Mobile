## 2. 必须保持的业务不变量

1. 先保存本机事实，再反馈“已保存在本机”；离线和电脑关闭不影响本地事务。未获对端持久确认不能显示“已同步”。本地提交不等待模型、地图、DNS或连接层。
2. 同一已提交操作只生效一次；同ID不同语义明确拒绝。失败不能只落账目却缺历史／操作回执，也不能只存待同步项却没业务变更。进程在提交后、桥接返回前退出，重试仍返回原结果。
3. 当前分支指向新的不可变业务修订；旧修订与其附件引用不改。用户可以明确更正／删除当前账目并留下历史，保护不等于永久禁止纠错；模型／规划结果不得替用户改实付、付款事实、回款或预约。
4. 行程日、付款日、预约当地时刻、记录创建时间分别表示不同事实。设备切时区、改行程顺序或重新生成路线，不自动改写付款日、稳定活动ID或预约时刻。
5. 预算／预测／未知费用与实付分开；未知不是0。退款与报销有独立记录、状态及原消费引用；不得通过改原消费金额表达退款或将报销重复冲减消费。
6. 删除、撤销、合并均是显式业务操作；历史及待同步删除记录保留。不能以清库、按更新时间覆盖整份旅行、复制活跃SQLite或重新生成所有ID解决冲突。
7. 凭据、设备私钥、配置秘密与本地文件绝对路径不进入业务快照／变更包／附件元数据。设备ID只识别来源，不代替配对认证；脱敏诊断也不输出整份旅行。

## 3. 金额、日期和身份的草案表示

### 金额

两端方向一致的新命令候选使用正整分JSON整数，避免JS先以浮点乘100；必须在桥接和原生落库前重复校验，不能依靠SQLite整数容量替代跨语言上界。金额文本严格解析属于新候选规则：输入框从十进制文本精确转换，建议拒绝指数、NaN、Infinity、非正实付／回款、超两位小数与溢出，不静默四舍五入或截断。电脑侧已实测旧Decimal接受指数、空白、前导零等形式，不能把建议写成旧接口当前行为；共同文本向量仍待固定。

单笔录入上界与汇总上界分开：电脑当前Decimal录入约束对应最多`99,999,999.99`元，即`9,999,999,999`分；它小于只读投影允许的正安全整数上界。候选先对齐现有录入范围，保留每分支2000笔消费／4000笔回款限制，不以P0大数样例扩大正式录入能力。每笔、每种汇总、中间累加与净额都检查安全整数范围，溢出拒绝整笔事务；Python读模型可接受超界整数不等于它符合0.1.0。用户已确认新写入首版显式CNY，其他币种另评审；旧缺失币种不推造CNY，不将未知币种金额混入新CNY总额或把旧超界数值裁剪成上限。字段与兼容细化见第9节。

### 日期与时区

| 语义 | 建议表示与处理 | 旧数据／未决项 |
| --- | --- | --- |
| 行程日 | 保留day序号及稳定活动关联；若增加日期，显式记录旅行日历映射 | 不能把day=2直接换成付款日期；修改出发日的联动规则待评审 |
| 付款日 | 用户已确认与行程日分开；新建消费默认填手机当前日期，可修改，也可主动选择未知，保存后不随时区／行程调整自动改变。确有付款时刻时另存带偏移的时刻及适用时区，具体编码待评审 | 旧模型无此字段，缺失保持未知；编辑旧记录不默认补今天，不拿created_at／行程日补造事实 |
| 预约 | 保留当地时钟、start_day_offset与duration_minutes；明确时区的新预约按用户确认的真实经过分钟计算，建议补所在地时区／解析信息及旅行日历基线 | 旧Booking未编码时区，保留原钟面规则、不批量重算；不能以手机当前时区默补。夏令时不存在／重复的时刻应提示并选择，不能偷偷挪动 |
| 创建／修改时间 | 新记录建议存明确定义的时间戳，仅作审计与展示 | 旧datetime来源可能无偏移，转换须保留未知来源；不作冲突排序或付款日权威 |

预填仅用于新建消费表单：保存用户提交的表单值，不在提交瞬间以当前日期覆盖；手机日期只是可修改的输入建议，不是付款事实的外部证明。旧记录编辑保持未知状态，除非用户明确补录。本轮只确认该使用规则，未注册字段、实现表单或写入数据库。

例如，用户确认付款日为`2026-11-14`，同时记录的时刻为`2026-11-14T00:30:00+09:00`；手机切到America/Los_Angeles后，这个时刻的当地展示为`2026-11-13 07:30`，付款日仍是`2026-11-14`。预约`23:40`／offset=0／120分钟，结束为次日`01:40`；不能将offset丢弃或把预约转换成手机所在时区的同名时钟。日历、时区库／数据版本与旧记录映射另给共同样例，本稿未新增日期算法。

| --- | --- |
| 旅行／分支／业务实体ID | 稳定且不由显示名称、数组位置或当天顺序生成；导入保留原ID，不强制把旧ID改成UUID。新ID格式／冲突域待共同固定 |
| 设备／安装身份 | 用于来源和去重；正常重开／升级不换身份。恢复备份、重新安装和多模式共存需另定防碰撞／重新配对流程，不能克隆身份冒充原设备 |

## 4. 本地命令与事务边界

建议应用用例通过窄命令提交语义数据，至少包含契约标识／版本、操作ID、来源身份、目标旅行／分支、期望基线、命令类型和参数。以下是语义族，**不是现有或已经确定的API名**：

| 命令族 | 应保护的状态与边界 |
| --- | --- |
| 消费／回款创建、更正、删除 | 金额、付款事实、预算／活动／票据关联与回款上限；同ID重放与关联删除规则 |
| 进度／预约更新 | 实际停留点、执行状态、当地时间与跨日偏移；已有执行记录时不能绕过规则直接更改预约 |
| 旅行／分支／版本／主方案操作 | 历史只读、主方案及父修订可追溯；只读历史编辑应成为显式新分支／修订，不原地改快照 |
| 计划／AI／高级工程结果采用或撤销 | 在线结果先存候选，应用时核对基线并重新执行保护规则；不能直接整包覆盖已记录事实 |
| 文件引用、回顾、偏好与工程本地管理 | 保护引用、权限和离线可读；设备配置与旅行数据分开。完整字段与规则按能力矩阵逐项补齐，不将本稿当仅支持记账的范围缩减 |

原生层负责最终边界校验及事务提交，不能因为TS已经校验就信任页面提交的总额、权限、SQL或文件路径。TS可复用领域计算与交互预检；规则所有权和两端参考样例需明确，避免两套校验悄悄分叉。建议第一版按分支串行提交并核对基线，在跨仓确认前不采用字段级自动合并或通用CRDT。

建议单次提交顺序如下：

1. 检查命令格式、来源／调用权限及支持版本，在固定编码规则下形成可比较语义。格式规范必须涵盖null／缺省、数组顺序、字符串和数字；不能随意用JSON.stringify结果充当跨语言指纹。摘要算法及测试向量待定，保留必要语义以诊断同ID不同内容。
2. 在同一受控写事务中先查操作回执：同ID同语义且已提交，返回原修订／结果；同ID不同语义，拒绝且原库不变。**已提交重放先于期望基线检查**，否则成功后回执丢失的重试会被错误判为过期。
3. 对新操作核对目标当前修订及删除状态，重新检查金额、日期／预约、预算／附件和全部关联约束。基线过期时返回可重新读取的冲突，不偷偷重定位到最新修订重放。
4. 原子写入业务新状态／不可变修订、分支头、操作回执、删除记录和待同步变更记录；派生账目从当前有效记录计算，不能把每个历史修订都重复计入。字段布局、快照或增量实现、索引及SQLite参数需后续评审，当前不建表。
5. 提交成功才回执本机保存；界面更新为“本机已保存／等待连接”。连接任务在事务外运行。这里的待同步记录是预留持久事实，不是已经可发出的协议包；协议／配对未就绪时不得发送或显示对端已确认。

中止前未提交：整笔无效，不能增加实付、修订或待同步项。提交后桥接断开：结果可能已成功，客户端保留原操作ID，查询原回执／同内容重试；不生成新ID补记。提交返回错误但结果不明时进入“结果待核实”，重新打开读取回执后判定，不能一律显示“未保存”诱发重复录入。读取失败／库损坏与空库分开，不创建空库覆盖原文件。

操作回执、删除记录和历史何时可清理需包含所有配对设备的持久确认／撤销策略；未定义前不按时间自动清除。界面撤销也生成新操作及修订，不能删掉已经确认的原操作来伪装从未发生。

### 附件与迁移

SQLite和文件系统不在一个事务。建议先把内容导入本应用拥有的暂存区，验证大小／类型／摘要并完成持久化，再让业务事务引用已就绪内容；业务提交后才清理暂存／旧引用。提交前退出留下的未引用内容可按明确归属清理，提交后退出的内容必须仍可读取；所有历史／待同步／备份引用都释放后才能物理回收。不得接受页面传入任意路径，不扫删其他应用文件，也不将content URI字符串当已永久复制成功。

磁盘满、权限失效、照片导入中断和附件缺失须有可恢复状态，不报告整笔完成；外部分享／系统选择器授权和跨卷移动需平台适配另验。文件就绪与数据库引用之间的崩溃点、备份一致性、恢复校验及清理时机均是实现前待细化项，不承诺简单rename能覆盖所有存储条件。

表结构升级须有旧版拒绝不兼容写入、隔离副本演练、恢复点及新增数据保全方案；回退不能直接用旧备份覆盖升级后新账目。P0的org.travelflow.p0虚构库不自动迁入正式产品。备份不含凭据，且不能用复制运行中的数据库文件充当业务同步。当前不迁移、清除或导出任何真实数据。

## 13. 原始JSON输入候选：先保真，再判断字段

### 本轮目标与复用选择

独立[58项原始输入](fixtures/p1-json-cases.json)接续电脑RAW1／RAW2，不改写历史三份JSON或vendor。每例提供`raw_json`字符串的UTF-8编码或`raw_utf8_hex`原字节，不能先用普通JSON.parse／float解码成业务数值再交本候选。资料自身的格式版本1只是样例容器，shared_contract_version仍null，desktop_joint_review仍pending。

未采用[lossless-json 4.3.3](https://github.com/josdejong/lossless-json/blob/v4.3.3/src/parse.ts#L69)：其重复键分支还要求新旧值不深度相等，同名同值会被放过；[LosslessNumber.valueOf](https://github.com/josdejong/lossless-json/blob/v4.3.3/src/LosslessNumber.ts#L48)亦允许部分浮点截断，不能直接作为精确整分判定。此结论针对固定版本与本轮需求，不评价所有用途。原生JSON.parse的source reviver不能恢复已覆盖的重复字段，亦不能默认旧WebView具备该能力。本次只选择宿主检查组件，正式移动端／原生解析器仍须分别验收。

### 候选处理顺序与可检查表达

1. 严格UTF-8解码，坏续字节、截断及直接编码的代理项拒绝encoding；BOM不静默删除，本候选拒绝json。
2. 严格JSON语法；注释、尾逗号、空文档、第二根值、NaN／Infinity、前导零／缺小数位与非法空白拒绝json。语法先于后续字段检查；不能消费容错恢复树。
3. 逐对象、按源码顺序检查**解码后的键名**，任何同名键均拒绝duplicate_key，包括同值、嵌套、数组内对象、转义后相同与`__proto__`。不同对象的同名键可用；不把这些键赋值到普通JS对象原型。键和值中的未配对代理项拒绝unicode，合法代理对可用；不做NFC、大小写或时区别名归一化。
4. 通用json profile保留数字词形为字符串，不全局强制整数或缩成双精度：大整数、普通小数、极大／极小指数都只作保真诊断，**不代表完整命令接受这些值**。有类型的诊断树使用`["object", [[key, child], ...]]`、`["array", children]`、`["number", lexeme]`、string／boolean／null等节点；对象／数组顺序保留，省略与显式null不合并。
5. 独立cny-amount profile只检查`currency`与`amount_cents`两字段片段：精确十进制值为正整数且不超9999999999分，显式CNY；Number／float之前的非零小数不能靠舍入通过。100、100.0、1e2均是整数值100；文本录入仍沿原MT严格语法，不因此允许用户输入指数。Node按十进制系数／指数做有界整数转换，Python用Decimal独立判断，不复用Node算法。

encoding／json／duplicate_key／unicode／amount等仅是候选错误类别，未注册产品码。诊断树保留数字词形和字符串语义，不保留全部空白／转义拼写，**不是规范化JSON、签名字节、命令摘要或同步载荷**。原值适配的raw_json_decoder_verified=false继续准确描述其解码后片段入口；新检查器另报宿主原型范围，不将其改成全局已验证。

### 语义等价候选，不是诊断树相等

建议对象字段顺序不影响合法命令语义；字段解释由命令配置决定，不能对任意JSON全局排序／数值转换。所有保留字符串先按JSON转义解码，保持Unicode标量序列，不隐式NFC、大小写折叠或语言运行时trim。标题旧strip的兼容映射须明示：本提案建议新命令按提交文本比较，表单若清理空白应在生成操作前完成并固定；旧记录／旧接口的显示与保存行为不据此批量重写。标题／备注长度拟按Unicode标量计数，而非JS UTF-16 length；字节预算另计，需补非BMP字符边界。收紧或转换规则需共同向量，不能直接用Python.strip与JS.trim当相同规范。

控制命令、完整快照／历史页与附件分开定预算，不能将一个小JSON实验的固定上限套到图片、2000笔消费或全部历史。正式边界至少需独立限制原始字节、嵌套深度、节点／键数、字符串与数字词形长度、并发／队列及总工作量；应在可能的递归解析／BigInt／Decimal分配前执行相应前置检查，成功与超限路径均不改业务库。具体数值、能力标识与原生实施尚未定，当前未做无界压力测试，不给宿主原型增加虚假的“生产安全”标记。

### 标量与文本合法性候选

本原型只对**新提交的title／notes**试行以下明确规则，待共同评审，不批量重写旧文本，也不把它说成全Unicode不可见字符方案：

- 按解码后的Unicode标量计长度，拒绝未配对代理项；标题1–100，备注0–1000；不trim、不NFC、不大小写转换。合法ZWJ组合保留，避免破坏多语言和组合字符。
- 标题拒绝C0（U+0000–001F）、C1（U+007F–009F）及U+FEFF；备注仅在C0中允许TAB／LF／CR，其余同拒绝。因此电脑反例U+001C、U+0085及U+FEFF有明确新候选拒绝结果，不借用运行时\S／strip。
- 标题须至少含一个不在固定空白表的标量：U+0020、00A0、1680、2000–200A、2028／2029、202F、205F、3000。C0／C1空白已在上一条拒绝；其他格式字符和非字符的正式域仍待定，不能据此声称I-JSON／JCS或“看得见”的判断已完成。标识符编码规则另定，不把这份标题表当通用ID白名单。

库只由SyntheticStore.create在宿主tmp中新建travelflow-p1-store-*目录，写入固定PURPOSE及fixture_*数据集／旅行／分支标记；构造器只打开该目录内synthetic.sqlite，缺文件或错误标记／格式直接拒绝，不重建空库。初始化失败只清理自己刚创建的目录，验收finally关闭并删除本次拥有的全部临时目录；仓库不保存SQLite／WAL／SHM或私有数据。当前每库一个虚构分支，格式1仅为宿主实验内部格式，未定义迁移。

fixture_branches保存当前业务JSON与头，fixture_revisions保存不可变快照／parent，fixture_receipts以数据集＋来源＋操作键唯一，fixture_outbox以同操作键唯一，fixture_tombstones保留实体类型／ID及删除修订；相关行以外键指向有效修订。SQL使用绑定值，逻辑时序为：

1. 原始资源／格式与虚构当前权限检查先于SQL事务；然后BEGIN IMMEDIATE。
2. 在同一连接／事务中先读持久回执，比对结构化原意图；同意图返回原effect／result_revision，异意图拒绝，不再加载或应用当前实体。
3. 对新操作重读权威分支头／快照／关联、核对基线并重新planIntent，不信任事务外的旧计划。预约按目标活动的day选择对应日历，不把首日日期套到其他行程日；缺失或不匹配拒绝。变化才生成新修订、业务快照及需要的墓碑，原历史行不更新。
4. 无变化保留原头和业务审计字段，但仍插入no_change回执与仅操作出站事实；result_revision指向核对过的已有修订，不伪称生成该修订。

## 22. 命令规范化字节／摘要与统一跨端验收入口

### 选择与精确字节范围

现有13种控制命令的数字字段均为精确整数，没有坐标小数。因而采用受限整数JSON编码，复用[RFC8785 §3.2的字符串转义、UTF-16键排序与UTF-8规则](https://www.rfc-editor.org/rfc/rfc8785.txt)，不实现通用浮点编码。原始近整数须先被精确字段校验拒绝，不能先用Number舍入再规范化。历史／坐标／任意旧快照的数值与字符范围还没有共同定版，不扩用此profile，也不声称完整JCS／I-JSON合规；既有非字符／Unicode标量策略保持。

Node使用内置[crypto.createHash](https://nodejs.org/docs/latest-v22.x/api/crypto.html#cryptocreatehashalgorithm-options)，Python使用标准库hashlib，无新依赖。摘要只作为内容比较候选，不证明来源或权限；正式采用仍须保存必要完整意图／字节，不能仅凭摘要相同替代当前授权和回执核对。本轮现有SQLite仍按完整结构比较，CandidateBoundary的canonical_bytes=false继续描述其未采用状态。

| 事项 | 本候选的确定行为 |
| --- | --- |
| 输入 | fingerprintIntent接原始UTF-8字节，control先经controlIntent，receipt-query先经queryIntent，保留原32KiB／8KiB及深度／token／字符串／数字词形预算。只做格式与字段校验，不读取当前基线、关联、权限或宿主时钟；编码成功不表示业务可提交 |

| 对象／数组 | 所有对象递归按解码后键的UTF-16无符号码元序排序，不能用locale或Python默认码点序。数组保序，其中对象仍递归排序；数字样式键"1"／"10"／"2"按文本序，不经JS对象再次序列化造成重排 |
